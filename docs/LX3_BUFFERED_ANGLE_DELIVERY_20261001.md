# LX3 버퍼 전달 시 조향각 제한 검토

USB에서 수락한 명령과 차량의 원본 CAN 슬롯에 삽입한 명령을 구분하도록
Panda의 LX3 개발 정책을 수정했다. 실차 경고 해소나 EPS 수신을 입증한 결과는 아니다.

## 재현한 결함

기존 각도 변화율 검사는 `safety_tx_hook`에서 수락한 마지막 USB 목표각을
기준으로 삼았다. 명령은 2개짜리 버퍼에 들어가며, 원본 카메라의 유효한
0xCB가 들어올 때 차량 방향 전달 프레임에 삽입된다. 수락과 삽입 사이에는
지연·큐 넘침·재사용이 발생할 수 있다.

측정각0에서 10ms마다2°씩 목표를 높이고 원본 슬롯을100ms 동안 주지 않으면,
USB 검사를 모두 통과한 뒤 첫 전달 슬롯에서18° 목표가 삽입됐다. 남은 큐의
목표는 수락 후10ms밖에 지나지 않아30ms 만료 검사도 통과했다. 실제 C를
컴파일한 회귀 테스트를 먼저 실패시켜 이 반례를 확인했다.

## 변경한 처리

- USB 수락 기준과 별도로 마지막 삽입 목표각·시각을 기록한다.
- 버퍼 pop과 reuse 직전, 삽입 기준으로 변화량을 다시 검사한다.
- 연속 삽입은 직전 목표각을 사용한다. 순정 프레임 복귀, 손상 원본 통과,
  비활성 삽입, 권한 회수, 초기화 또는30ms 이상 공백 뒤에는 측정각으로 시작한다.
- 기존2°/10ms 제한과 반올림1 raw 여유를 유지한다. 경과 시간 예산은10ms로
  제한하며, 버퍼 적체를 이유로 목표를 몰래 잘라 맞추거나 허용치를 늘리지 않는다.
- 전달 변화율 위반이면 `lx3_clear_session()`으로 accepted 권한과 모든
  actuator 버퍼를 해제한다. 정상 물리 버튼 스트림의 준비 상태는 유지한다.
  오래된 USB 목표나 ACK만으로 다시 활성화되지 않는다.

LX3 guard1024에만 적용한다. 다른 차종이 사용하는 기존190 정책과 기존
긴급 순정 신호 복사 목록은 유지한다. 제어 프로토콜이나 health ABI는 바꾸지 않는다.

## 검증

엄격한 C 경고와 UBSan으로 컴파일한 기존 native 회귀,64개 구성 호환성,
20,000개 상태 혼합 검사를 통과했다. 새 영구 회귀에는 양방향 적체,
두 목표 FIFO, 큐 넘침, 같은 시각의 두 번째 출력, 정상 EPS 추종 지연,
OFF 후 측정각 기준 재진입, reuse2회 후 순정 복귀, 원본 CRC/길이 불량,
30ms 경계, MCU 타이머 wrap, 해제 직후 coherent idle companion을 포함한다.

production host와 실제 Panda C를 연결한414개 합성 일정 중54개는 정상
물리 버튼/ACK 거래로 권한을 얻은 뒤 이 출력 위반을 유발한다. 모두 native
권한이 해제됐고, stale host 송신5,184개가 거부됐다. host도10Hz companion
보고를 받아40–90ms 뒤 해제됐다. 실제 msgq·USB·차량 ECU의 지연 측정은 아니다.
기존 표시40개 위상/jitter 일정도 통과했다.

PC의 Python202개 회귀는 통과했다. 직전 커밋9bb19a48은 GitHub
run36757993842의5개 job을 통과했으며, 실제 Linux Params/CarInterface/
generated DBC/CarController 설정3개 검사, msgq·Capnp·AlertManager,
깜빡이9개 검사, 전체 runtime graph와 H7 빌드를 포함한다. 본 변경의 정확한
커밋별 CI 결과는 PC 검증 manifest와 Actions에서 별도로 확인한다.

실제 Claude 동일 세션14·15차는 같은 결함과 구현을 읽고 반례를 교환했다.
15차는 새 우회 경로를 찾지 못했으나 EPS 추종 지연에 따른 보수적 해제와
측정각50ms 신선도의 한계를 지적했다. 실행 로그와 CI를 독립 실행한 것은
아니다. 제안된20ms 새 임계값은 실차 근거 없이 추가하지 않았다. 이미 영구
회귀는 측정각0·목표10° 상태에서 손상 원본 뒤 해제되는 경우를 고정한다.

## 가용성과 관측 한계

과거78개 기록에서 순정 CB529,337개와 USB 요청522,590개를 대조했다.
기록 시각 기반의 단순 버퍼 모델에서 활성 삽입 후보121,658개 중291개가
새 변화량 기준 밖이었다(연속289, 재시작2). 큐 넘침 후보1,120개도 있었다.
모델은 당시 요청의 native 수락 여부, 권한, 운전자 개입을 재현하지 않고,
위반 뒤 실제 새 정책이 요구하는 세션 해제도 실행하지 않는다. 따라서291개를
실제 오탐·해제 횟수나 새 버전 결함으로 계산할 수 없다.

원본 CB529,337개와 MDPS529,263개는 CRC가 모두 유효했다. CRC가 유효한
활성 명령 echo와50ms 이내 원본 MDPS의 대응121,733개 중5,942개는 두 각도가
21raw보다 달랐다(상속 DBC 기준2.1°).70개는 MDPS가20ms보다 오래됐다.
추종 지연이 있으므로 연속 출력 중 측정각 기준을 매번 다시 쓰지 않는다.
이 차이 비율을 EPS의 결함이나 새 버전 해제율로 해석하지 않는다.

특히 순정 CB36,867개는 직전 프레임과 같은 host batch 시각이었다. 실제 MCU
수신·출력 시각과 다르므로 이 자료만으로10ms 예산을 완화하지 않는다.
손상 슬롯이나 순정 복귀 뒤에는 정상 EPS 추종 지연으로도 해제될 수 있다.
출력 간격·각도·실제 EPS 응답을 함께 측정하는 qualification이 남아 있다.

삽입 기준은 firmware forwarding hook의 결정이다. 이후 `can_send` 실패,
bus-off, 중재 지연과 EPS 수신·수락을 보장하지 않는다. 송신 echo도 실제
차량 수신 증거가 아니다. 개발 후보의 `dashcamOnly`는 유지하며 본 작업에서
차량 설치·재부팅·OTA 배포를 수행하지 않았다.

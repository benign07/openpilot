# 매 운행 자동 기록

사용자는 진단 버튼을 누르지 않고 평소처럼 운전한다. `carrot_server` 시작 시 별도 작업 스레드가 신선한 `deviceState.started`를 확인해 자동 기록한다. HUD/휴대폰 연결 유무와 오파 활성 여부는 수집 시작 조건이 아니다.

**2026-09-28 정차/P 상태에서 기기 적용·전체 재부팅과 Xiaomi 15 HUD 1.0.11 설치를 완료했다.** 기기 적용 소스는 `10434d6ab0a0217d13d2844801ff16a5258a13b9`, APK 빌드 소스는 `b8d32b71a551c090390b6849ccf57a614b00c97a`다. 조향·제동 설정은 변경하지 않았다. 아래 검증은 정차 조건의 결과이며 실제 도로에서 최초 주행보조 경고가 해결됐다는 의미는 아니다.

## 수집 내용과 한계

- 5 Hz: 속도·가속도·페달·조향·방향지시등·사각지대·순정 크루즈 상태, 실제 횡/종 제어 상태, 앞차, 종방향 계획, 경고 문구. 서비스 원래 `logMonoTime`, `valid`를 함께 보관한다.
- 직접 운전, 순정 크루즈, 오파 횡제어만/종제어만/둘 다, 대기, 불명 상태를 구분한다. `AlwaysLateral` 때문에 오파 활성 표시가 꺼져 있어도 횡제어가 켜질 수 있으므로 `carControl.latActive`를 별도로 확인한다.
- 선택 CAN 주소 `0x161/0x162/0x1EA/0x2A4/0x362/0x1A0`: 방향·버스·주소·길이별 최대 10 Hz 표본을 보관한다. `rx`, `tx_requested`, `tx_echo`를 구분한다. 물리 ECU 발신 주체는 버스 번호만으로 확정하지 않는다.
- LX3의 `0x162` FAULT_LSS/DAS 값 변화는 표본 제한과 별개로 해당 프레임과 함께 기록한다. DBC 정의를 읽은 관측값이며 원인 확정이나 경고 해결의 증거가 아니다. 수신 지연·구독 시작 전·유효하지 않은 패킷의 사건은 놓칠 수 있다.
- 제어 상태 변화, 브레이크 입력, 제어 중 운전자 조향 개입, -2.5 m/s² 이하 감속, 앞차 상태의 반복 변화를 자동 표식한다. 이 임계값들은 검토할 사건을 찾기 위한 것이고 차량 제어 임계값이 아니다.
- `boot_id`, `trip_id`, `CurrentRoute`, 소스/DBC 해시, 설정을 보관한다. 시동 정보가 끊기거나 서버가 재시작하면 같은 실제 운행도 별도 기록 구간이 된다. PC의 ‘구간 수’는 독립 운행 횟수의 확정값이 아니다.
- 영상, GPS, 전체 CAN을 중복 저장하지 않는다. 선택 CAN 표본에는 생략이 있으므로 카운터 연속성·정확한 주기 검증에 사용하면 안 된다. 기존 rlog의 전체 CAN과 단조 시각으로 대조해야 한다.
- **rlog 전체의 자동 보존/휴대폰 전송은 이 버전에 포함하지 않았다.** 기기 로그 순환 전에 별도로 가져와야 한다. 서버 시작 이전 부팅 구간도 이 수집기로 소급 복원되지 않는다.

## 저장·전송

`/data/community/automatic_drive`에 60초 또는 원문 2 MiB마다 압축 파일과 SHA-256 manifest를 확정한다. 확정된 파일만 HTTP 다운로드와 Range 재개를 허용한다. 수집 중 파일은 공개하지 않는다. 원문은 1초마다 flush/fsync하고 재시작 때 완전한 JSON 행만 복구한다. 급격한 전원 차단 때 마지막 미동기화 구간은 유실될 수 있으며 복구 파일은 미완료로 표시한다.

기기 기록 상한은 512 MiB, 디스크 여유 하한은 512 MiB다. 용량 부족이면 기존 기록을 삭제하지 않고 상태를 표시하며 수집을 중단한다. 자동 정리·전송 확인 후 원본 삭제는 포함하지 않는다. 따라서 무기한 무인 수집을 보장하지 않는다.

API:

- `GET /api/automatic_drive/status`: 기록/정지/오류/용량 상태
- `GET /api/automatic_drive/chunks`: 완성 파일의 식별자·크기·해시·종료 사유
- `GET /api/automatic_drive/chunks/{id}`: 압축 원문, Range 지원

기존 웹 서버와 같은 접속 범위를 사용한다. 수집 파일이나 원본 rlog를 GitHub에 올리지 않는다.

PC에서 기기가 연결될 때 자동으로 받아 분석하려면:

```powershell
python tools/can_auto_sync.py --url http://100.98.217.122:7000 --out 'D:\CarrotDriveRecords' --watch
```

이 명령이 실행되는 동안 60초마다 이어받기·해시 확인·중복 제외·분석 보고서 생성을 수행한다. Windows 시작 작업 등록은 하지 않았다. 휴대폰 내보내기 ZIP을 압축 푼 기록은 다음과 같이 분석한다:

```powershell
python tools/can_auto_sync.py --out 'D:\CarrotDriveRecords' --analyze-only
```

출력은 `analysis.json`, `analysis.md`다. 속도대와 제어 상태별 가속도/차간 시간 분포, 반복 사건, 손상·복구 파일 수를 집계한다. 원인을 확정하거나 운전자 취향으로 학습했다고 표시하지 않으며 Params/CAN 송신 경로가 없다.

휴대폰 대응 소스는 `benign07/carrot-hud`의 `automatic-drive-archive` 브랜치다. HUD 또는 기존 오버레이를 사용하는 동안 native worker가 파일을 자동 보관한다. 앱을 강제 종료해도 계속되는 상시 서비스/부팅 자동 실행은 포함하지 않는다. 두 화면을 모두 닫으면 전송이 대기하고, 다음 연결에서 이어받는다.

## 2026-09-28 적용 및 검증

- 실기기 격리 경로에서 자동 수집/복구/모드 구분/전송/API와 기존 진단 테스트 46개 통과. 기기의 typed Params API에 맞게 읽기 호환성을 수정했고, 5 Hz로 필요한 필드만 추출한다.
- 신선한 P단·속도 0·CAN 유효·횡/종/자율 제어 해제를 연속 확인한 후 원본 백업과 해시 검사, 7개 파일 원자 교체, 전체 재부팅을 수행했다. 적용 후 7개 해시 일치, 보관한 설정 154개 불변, 주요 프로세스 8개 실행, CAN 유효, 자동 기록/API 정상 동작을 확인했다.
- 정차 30초 관측에서 전체 `carrot_server` CPU는 단일 코어 기준 약 18.8%, RSS 약 107.4 MiB였다. 이는 전체 기기 CPU나 순수 추가 비용이 아니며, 주행 중 부하/장시간 안정성 측정은 남아 있다. 관측 중 수신 지연에 따른 CAN 폐기 카운터는 0이었다.
- 완성 파일의 선택 CAN 6,315개를 대응 rlog 두 구간과 대조해 바이트·시각·방향이 모두 일치했다. 신호 의미나 전체 CAN 수집 완전성을 검증한 것은 아니다. 초기 차량 식별 전 파일 한 개는 차량/route 메타데이터가 없었고, 분석기는 초기 유효하지 않은 문맥을 제외한다.
- Xiaomi 15에서 HUD 1.0.11 설치와 데이터 수신을 확인했다. 자동 보관한 13개 파일의 크기·SHA-256이 기기 manifest와 일치했고, 그중 먼저 PC에 받은 11개도 동일했다. Android 전송 JVM 테스트는 5개 통과했다.
- 휴대폰 ZIP 내보내기와 화면 꺼짐·오버레이·연결 단절 뒤 복귀는 실폰 검증이 남아 있다. 실제 자동 보관 동작과 별도로 확인해야 한다. 장시간 무인 수집, 운전 성향 학습, 최초 주행보조 경고 해결은 아직 검증하거나 구현하지 않았다.
- 원본 소스/설정 및 기존 휴대폰 APK는 비공개 로컬 백업으로 보존했다. 이후 다시 적용하거나 복구할 때도 신선한 정차 상태와 해시를 확인하며, 기록을 보존한 채 해당 소스 변경만 복구한다.

향후 제어 개선은 충분한 정상/문제 구간 비교 → rlog 재생·회귀 검증 → 제한된 후보값 → 정차 적용 → 되돌리기 가능한 비교 순서로 진행한다. 현재 구현은 그 근거를 자동 수집하는 단계다.

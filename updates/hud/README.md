# 오파 GitHub 업데이트 관리

## 변경부터 실기기 검증까지

1. **기기 기준 확인:** 실제 설치 파일의 해시와 설정을 확인하고 소스·설정을 비공개로 백업한다. GitHub와 기기의 차이를 확인한 뒤 변경 범위를 정한다.
2. **소스 변경·검증:** 작업 브랜치에 목적별 커밋을 만들고 관련 테스트와 GitHub Actions 결과를 확인한다. 배포 기록에 테스트한 소스 커밋과 CI 링크를 남긴다.
3. **배포본 작성:** PC에서 그 소스 커밋으로 서명된 bundle을 만든다. 버전, 증가하는 sequence, 변경점, 대상 차량, 파일별 적용 전후 해시를 고정한다.
4. **GitHub 게시:** bundle을 커밋한 뒤 그 커밋과 해시를 `latest.json`에 고정한다. 공개 주소에서 내려받은 파일의 해시·서명·소스 일치 여부를 검증한다. `releases/<버전>.md`를 작성하고 해당 인덱스와 기록을 포함하는 커밋에 같은 이름의 annotated tag를 붙인다. 게시한 태그와 bundle은 덮어쓰지 않는다.
5. **HUD에서 선택:** 앱에서 변경점을 읽고 표시된 버전을 예약한다. 운행 중에는 예약할 수 있고, 실제 적용·재부팅은 기기가 P·정지·제어 해제와 최신 CAN 상태를 확인한 뒤 진행한다.
6. **적용 결과 기록:** 재부팅 후 파일 해시, 설치 버전, 필수 프로세스와 기능을 확인한다. 차량에서 확인한 항목과 남은 검증을 해당 버전 문서에 날짜와 함께 추가한다. 기존 버전 태그는 움직이지 않는다.

`GitHub 게시`, `소스 테스트 통과`, `실기기 적용`, `기능 검증`은 각각 다른 상태다. GitHub에 파일을 올렸거나 태그를 만들었다는 이유로 기기에 설치 완료된 것으로 기록하지 않는다. 태그는 코드와 배포 기록을 고정하는 용도이며 GitHub Releases 게시물과는 별개다.

문제가 생기면 다음 배포와 적용을 보류하고 기기 로그·백업을 확인한다. 이전 코드를 다시 배포할 때도 새 버전과 더 큰 sequence, 현재 기기의 before 해시로 복구 배포본을 만든다. 이전 `latest.json`으로 돌려놓는 것만으로 기기가 되돌아가지는 않는다.

## 보관 범위

GitHub에는 소스, 공개 가능한 배포 명세·서명된 bundle, 변경 이력과 검증 결과를 보관한다. 원본 주행 기록, rlog, Params 백업, 개인 위치 정보, 연결 토큰과 서명 비밀키는 비공개 PC 저장소에 보관한다.

최초 업데이트 기능 설치, 배포 가능 파일과 복구 제약, 실제 명령은 [업데이트 구현 안내](../../selfdrive/carrot/hud_update/README.md)를 따른다.
